# TH18 子弹覆盖与更新顺序审计

> **版本**：TH18 v1.00a，imagebase `0x400000`。样本 `local/th18.v1.00a/th18.exe`，本次重算 MD5 `9969cac756098c1da05a81de45437a70`。
> **方法**：当前 `mods/th18.v1.00a/autoplay/native/th18_extract.c`、patch JS，与样本 objdump 逐指令核对；本机已缓存 HTML / ExpHP 结构只作为定位补充。没有打开 Ghidra 工程，没有修改生产代码，没有运行游戏。
> **范围**：链表、flags/state 过滤、出生/更新/碰撞顺序、速度语义。不复核半径公式、模型数量上限。

## 已确认结果

1. ✅ 当前 `manager+0xc0` 活动链入口正确；未发现需要另扫一个普通子弹池的证据。
2. ✅ `flags&0x100` 的正常 state1 / 晚期 state2 只擦弹、不致死，不能把所有这类可见对象当作漏掉的致死弹。
3. ✅ `state2 timer<8` 的常规生成阶段不会因为 timer 在同一 tick 先加一而突然致死。原生先判定，最后才增加 `+0xf70`。
4. ✅ 有一处具体时序遗漏：state1、flags0x200、EX `+0x684&0x04000000`、等待 `+0xe68<=0` 的对象，在本次原生更新中会清掉0x200并恢复移动/致死判定；提取器在更新前已经跳过它。它在恢复后的第一次碰撞 tick 没有进入 world。
5. ✅ state2 并非整个下一 tick 一定只走半速。ANM I0 非零时，它半步后转成 state1，随后可以再走完整一步并再次判定。当前 `vx/vy×0.5` 仅准确描述前半段。
6. ✅ hook 发生在玩家 priority0x17，敌人0x1b、子弹0x1d之前。新生成弹与本帧 EX 变速只能在之后发生；不能把截图里比提取时刻更新的弹全部解释成漏链。

以上第4项是本次新证明的局部覆盖差异；尚无实机失败帧，不能认定它就是用户报告的主要原因。第5项是速度语义差异。第6项是既有采样时点限制。矩形弹在当前代码中明确不输出，是否致死及覆盖方案由几何审计另报。

## 1. 活动链与池的身份

**发现**：`0x424c7e` 从 manager+0xc0 开始，`0x424c92` 取 node+4 下一节点，`0x424c97` 取 node+0 子弹对象。构造 `0x423c9a` / `0x423ca6` 分别清空内嵌哨兵 content / next。

**候选解释**：+0xbc 是哨兵对象，不是首节点槽；另有空闲链可能被误作第二条危险链。

**验证**：发射函数 `0x424fe0` 在 `0x424ff1` 从 manager+0xb0 取空闲对象，无空闲时直接失败；`0x42500a` 至 `0x425024` 把它从空闲链摘掉，`0x42502a` 取对象+0x10 的活动节点，再插入 manager+0xbc 哨兵后的链。销毁函数 `0x424ad0` 先将 state=0，`0x424bb5` 起接回 manager+0xac 的空闲哨兵，随后 `0x424c19` 起摘掉对象+0x10 的活动节点。构造器 `0x423c31` 至 `0x423c98` 用 stride0xfa0 建2000个空闲对象；该范围本身不会超过提取器2002节点遍历限。

**结论**：✅ TH18 本条活动链正是 BulletManager 更新/碰撞使用的集合。manager+0xb0 是空闲对象入口，manager+0x10/+0x28 是更新时重建的绘制分类链（`0x424d81` 至 `0x424dbf`），不能为了多收可见弹而扫这些链再合并。对完整正常活动链，当前遍历入口和2002步限没有新发现的丢弹错误。

对 `0x45cd90` 圆判定与 `0x45cc20` 矩形判定的直接调用作了交叉搜索：普通子弹在 `0x42490b` / `0x42493f` / `0x42494b`；圆形敌人接触另在 `0x42f580`。这不是“全游戏不存在其它伤害源”的证明；激光另有入口，自定义敌人接触也可以间接调用。未建立需要新增普通弹池扫描的证据。

## 2. 过滤与“可见”和“可致死”的区别

| 提取器条件 | 原生证据 | 审计结论 |
| --- | --- | --- |
| flags缺2 | `0x4248cf` 直接跳过判定 | ✅ 当前碰撞函数确实不用它 |
| flags8 | `0x423ea4` 跳到销毁 `0x424888` | ✅ 普通更新下在碰撞前删除 |
| flags0x100 | manager `0x424d33` 至 `0x424da3` | ✅ state1/晚state2走param=1，只擦弹 |
| state3 | `0x423f0e` 至 `0x423f7f` | ✅ 半速收尾，无子弹致死判定 |
| state4等其它状态 | `0x423f11` 跳 `0x424617` | ✅ 无该普通弹致死判定 |
| state2、timer<8 | `0x423f84` / `0x423ff3` | ✅ 跳过半步后的判定；I0转态例外见后 |
| state1、flags0x200 | `0x4245a9` | ⚠️ 最终门正确，前置快照不一定等于最终flags |

### 0x100 不是待恢复的一整类致死弹

**发现**：manager 先查0x100。若 state1，或 state2且timer>=8，跳过 Bullet::on_tick，只调用 `0x4248a0`，传入1（`0x424d9f`）。没有先走本体里的param=0判定。

**验证**：`0x4248f2` 将这个参数传给具体碰撞；圆判定 `0x45ce52` 在非零参数时返回2，不进入 `0x45ce63` 后的玩家死亡路径。因此此前“只看本体有param=0调用就断定0x100会杀人”的假设被manager控制流否定。

**结论**：✅ 对正常state1/晚state2，这个排除不漏掉致死判定，即使这些对象还被画出来。理论例外是早state2在同tick由ANM I0切成state1；manager早state2会进本体。当前未证明原生常规脚本在timer<8产生此组合，不能据此宣称0x100过滤已发现实际bug。

### bit2 的本帧变更

发射时 `0x4256bc` 至 `0x4256d9` 清擦弹/删除位并设置bit2。对已缓存 `Bullet::run_ex` 全体与本次指令定位，直接针对子弹flags+0x20的写入只有形状bit0x10、scale bit0x40；本体另有0x200处理，取消/回池另有清位。没有找到自己的EX在下一次判定前把缺失bit2重新设置的路径。因此“缺2过滤会漏掉本帧恢复碰撞的弹”目前没有证据。这里的否定只覆盖已读普通弹EX路径，不外推到所有间接回调/插件。

## 3. flags0x200 恢复时的第一次致死 tick

**发现**：提取器第84行在玩家入口看 state1&0x200就continue；原生最终门 `0x4245a9` 在EX更新之后。

**假设**：对象在本次EX更新中解除0x200，前置过滤遗漏它第一次恢复的碰撞。

**验证**：`0x424030` 检查EX位；`0x424036` 的0x04000000会跳过 run_ex，进入现有行为处理。`0x42444e` 再测此位，`0x42445a` 读等待计数 +0xe68。计数<=0时，`0x42446a` 清EX位，`0x424470` 对flags执行AND0xfffffdff，`0x42447c` 写回。随后仍可到 `0x4245b2` 移动和 `0x424612` param=0判定。计数>0时则 `0x424511` 设置0x200并递减计数，到末尾跳过移动/判定；manager依然会增加生成timer。

**结论与时间线**：✅ 原生可达控制流已证明；实际关卡出现频率未证明。令最后一帧等待前计数为1、其它条件允许致死：

- tick N的hook：state1、0x200、计数1，被跳过。原生维持0x200，计数1→0，不碰撞。
- tick N+1的hook：state1、0x200、计数0，仍被跳过。原生清0x200，恢复移动，并在新位置作致死判定。这一tick world缺该弹。
- tick N+2的hook：已清0x200，才重新输出；这不是漏链，而是前置flags过滤比原生最终门早了一帧。

原生同tick还可能接着执行EX，再次设置等待或取消；不能保证所有满足入口字段的弹本tick最终一定致死。小范围修正可只识别这项已存在等待的到期门、按恢复对象保留；具体实施须避免把整个EX未来模拟扩展进提取器。此次没有实现。

## 4. state2 阈值及转态速度

### timer7→8 没有额外同帧漏洞

**发现**：本体入口确实先更新一个timer，但 `0x423e15` 至 `0x423e9e` 更新的是 +0xf84，不是 +0xf70。

**验证**：生成timer `+0xf70` 在manager `0x424dc5` 至 `0x424e28` 里，位于本体/碰撞之后。state2阈值在 `0x423f84` 读旧值；0x100分支也在 `0x424d48` 读旧值。

**结论**：✅ hook看timer7且I0=0 → 本tick只半步，不致死 → manager末尾改8 → 下一hook输出timer8 → 原生本tick第一次常规致死。当前>=8不需要减成7。早期可见生成特效没有进入world与此一致。

### state2 最后一帧可能移动1.5步

**发现**：state2总是先做0.5×dt速度移动；若timer>=8，先在半步后判定。若未命中1，`0x424007` 读ANM整数变量I0（bullet+0x4cc = 内嵌VM+0x28+0x4a4），非零时 `0x424019` 写state1，并直接落入state1 EX和正常移动/判定。

**验证**：本机解包 `anm/bullet/bullet.anm.txt` 的script35至42等，将I0先设0、生成动画8/15/25帧后设1。原生在本体末尾 `0x424879` 执行ANM，故下一hook可观察到仍state2但I0=1的过渡组合。没有完整枚举所有脚本，也没有实机捕获这种过渡组合。

**结论**：✅ 这条控制流不符合提取器第101行“state2下一tick固定半速”的无条件说法。无额外EX时，未命中第一个位置的弹还会从半步位置再走1步，在总1.5步位置作第二次判定；有EX则第二步还可能变速。仅把state2速度换成1.5也会丢失中间那次碰撞，不能称完整复现。可先把文档改成前半段速度，并在后续确有需要时对已有I0过渡字段作局部处理，不需要新建跟踪状态机。

对timer<8、I0非零组合，原生也能提前转state1后致死，当前state过滤会漏它；但常规生成脚本最短8帧的样本不支持把它当作已出现的bug。须与上面的已证明等待到期差异分开表述。

## 5. hook、出生、EX 与截图的先后

**发现与验证**：patch在 `0x45be90` 玩家body入口。wrapper `0x45caa0` 尾跳这里。玩家注册priority0x17（`0x45a8aa`）；敌管理器priority0x1b（`0x42dcce`）；子弹priority0x1d（`0x423bd8`）。注册函数 `0x4011d5` 至 `0x4011e2` 按优先级升序插入。普通发射将对象插入活动链（第1节），初始化state1于 `0x425254`，除非EX后来进入state2。

**结论**：✅ 时序是：本帧输入装配 → hook提取旧弹位置并决定输入 → 原生玩家移动 → 敌人更新/ECL可发弹 → 子弹EX/移动/碰撞 → 后续绘制。敌人本帧新发的普通state1弹可能本帧就碰撞，却尚不存在于hook的活动链快照；下一次hook才可读取它。同理，+0x644/+0x648给出的是EX处理前存量速度，原生state1先执行 `0x424040` run_ex和其它行为，再在 `0x4245b2` 移动。当前v×dt适合无EX变更的直线弹，不是所有本帧运动的精确导数。

这既解释“画面有更多对象”可能来自时点差异，也不能证明用户那一帧就是正常延迟。此次没有实机snapshot/截图同帧对齐证据。没有建议改hook架构、扫描未来对象或添加推断池。

## 补充：原生 ECL 里哪些普通弹是矩形

用户追加要求后，检查了已解包的原生 ECL。`local/th18.v1.00a/ecl/` 有21份文本；缺失的st07主道中使用现成 `local/vendor/thtk/build/thecl/thecl -d 18 -m local/vendor/eclmap/eclmap/th18.eclm` 从本机 `dat/st07.ecl` 反编译到本次临时目录，合计覆盖22份原生ECL资产。未下载或入库游戏数据。文本按 `errors="surrogateescape"` 读取，未因Shift-JIS字符串中断搜索。

**发现**：ECL `etSprite` 选择图案/type和颜色，并不能按肉眼外形推断碰撞几何。几个可复核的实际调用是：

- `st01bs.ecl.txt:142`，`Boss1_at_et`：`etSprite(0, 8, $D)`。
- `st04bs.ecl.txt:87`，`Boss1_at`：`etSprite($A, 44, 1)`。
- `st05bs.ecl.txt:657`，`BossCard1_at`：`etSprite($A, 16, $I0)`。

**验证**：与原生几何审计者交叉核对：原生初始化 `0x425795` 在48类型分派之前无条件OR flags0x10（圆碰撞）；类型表的+0x10c分类是取消效果分类，不能当圆/矩形开关。本人读过的完整 `Bullet::run_ex` 中，指向普通弹flags+0x20的直接写入仅有类型变更时OR0x10（`0x42647e`）、取消效果类型分派时OR0x10（`0x426659`）、尺寸缩放时OR0x40（`0x426e9f`）。EX尺寸缩放不会因此改成矩形。`0x4248fd` 的矩形消费者确实存在，但“有矩形判定函数”不能证明任意普通弹type会走到它。

**结论**：✅ 在已核对的原生48类型初始化与普通ECL/EX路径中，没有建立“哪一种普通子弹属于矩形碰撞”的正例；目前不能列出一个有证据的矩形普通弹类型。激光的矩形判定属于另一套集合，不能反推普通弹类别。这比把长条、札弹或刀形外观直接标为矩形更可靠。

**边界**：ECL有动态type表达式，例如 `st04bs.ecl.txt:1020` 的 `BossCard3_at2` 使用 `etSprite($C,$A,$D)`，`st05.ecl.txt:712` 使用 `$I0`；本次没有完整执行所有难度/参数分支。也未证明所有间接回调、外部插件绝不修改flags。本文没有凭字符串grep宣布EX_HITBOX“全游戏不用”；它不是已验证的矩形切换开关。上述结论限于已读原生普通弹生成/EX机制，不能替代同帧运行日志。
