## 目标与范围

把一份已明确边界的原作攻击，稳定交给模型作者、目标程序验收器和独立审核者；扩作品时主要补本作源材料、切分/摘录逻辑、映射及限制，不再复制整套调度程序。

第一阶段接通 TH18 单攻击和小批量写审。切分仍允许人工/AI完成，经主会话确认后交接结构化清单；不要求先造完整现代 ECL 语义分析器。现有 TH06 命令与生产记录继续可用。

保留 main.ecl 与 meta.toml 的卡产物形式；卡目录及少量分类字段调整见新增卡池提案。本轮不改引擎、训练模型、reward或 Python 依赖，不实现曲线激光，不重转旧卡，不启动整关付费批次或训练，不自动提交/推送。租机和部署不在范围内。

## 方案取舍

1. **共用流程＋作品适配（用户已选）**：复用模型执行、验收、返工和审核交接；作品只提供源理解与知识。需要逐步解开现有全局路径，但新增作品的维护量较小。
2. **独立 TH18 流水线**：初期复制快，但模型调用、审核和报告会形成两套实现；不符合继续扩作品的目标。

不引入插件框架、数据库、任务服务或自动恢复系统。普通 Python 模块与显式配置已足够；未知问题提示并人工补资料/重派。

## 模块与依赖方向

```text
CLI（选择作品、阶段、单元）
  └─ 共用流程：准备 → 转写 → 验收 → 独立审核 → 抽检清单 → 人工确认收卡
       ├─ 作品适配：源定位、切分材料、原样摘录、参考资料、作品规则
       ├─ worker：沿用 dsh-flash / claude-worker 进程协议
       └─ 目标工具：现有 validate / harness / preview
```

- **共用流程**只认识准备好的单元、文件位置和结果；不识别 TH06 opcode 或 TH18 的 MainSub/EX。
- **作品适配**提供准备单元和构造写审资料的普通函数、配置。TH06 的解析/闭包不导入 TH18 模块，TH18 也不调用 TH06 摘录注释。
- **worker**从现有 `run_worker` 拆出执行和日志逻辑，不在这里决定坐标、时限、弹型或切分边界；默认后端不变，Sonnet并发4约定不变。
- **目标工具**保留现有编译与四层验收行为。按作品读取编号/预算规则，源语义仍交独立 reviewer；引擎默认路径与作品源路径分开。

拟定代码归属：`pipeline.py` 保留 CLI/编排；`worker.py` 放现有调用；`games/th06.py`、`games/th18.py` 放适配；共用小型任务结构放 `tasks.py`。现有 TH06 解析器可先留原文件，由 TH06 适配调用，不先做全包改名。`config.py` 管共用路径，作品配置各自管理源材料。

这些是具体实现建议；实施时允许合并过小的模块或调整函数名，不能改变职责、扩大权限或另加机制。

## 输入与产物约定

保持目标卡 `main.ecl`、辅助 `.ecl`、`meta.toml` 格式。新增作品的任务准备使用小型 JSON 清单，不让调度器从 Markdown 自由文本猜执行参数。

TH18 阶段目录继续为 `work/th18/stage01/`；保留 `sources.json`、`structure.md`、`split.md`。阶段清单 `units.json` 由人工/AI依据已确认切分编写，主会话核准后供 `prepare` 使用。每条仅包含实际交接所需信息：

- 最终 `id`、原切分标签、kind、rank连续区间、目标时限与源时限依据。
- 源文件路径、原文行区间、入口和依赖；行号始终对应完整源文件。可包含多个文件和多个区间。
- 段入口状态、源/卡帧对应、已接受差异、实际阻塞原因。
- 所需参考页/词表路径、任务说明。作品、版本和源根目录可在阶段级声明，不逐条重复。

`prepare` 按清单原样摘录，保留文件和行区间标记，不改写原文；仅检查输入能否读取、行范围/编号/rank等执行所需参数是否有效。它不证明语义闭包完备或整关覆盖；这些由切分审阅负责。首版无需自动反编译或复用不兼容的 raw parser。

每单元写入 `stage01/<unit_id>/`：

```text
unit.json、brief.md、source.txt、references/  输入与本次参考副本
out/                                       作者交付及 validate.json
card/<unit_id>/                             完整目标验证副本
review/round-0/、review/round-1/             独立审核输入、verdict与日志
```

参考副本保留其原目录层次，使 Markdown 相对链接可读；原引擎文档/只读原文也可明确路径引用。审核输入从本轮材料复制，附实际目标文件和验收报告；复审保留上一轮，不构造复杂快照存储。目标行为修改后同步验证副本，补受影响的运行检查和审核；纯文案修改不自动触发整轮重验。

新 TH18 状态放 `work/th18/state.jsonl`，沿用已有状态含义和人工分诊方式。现有 TH06 `work/state.jsonl`、units/review/split/logs 保留；通过路径配置适配，不迁移/伪造历史事件。两作状态不串读。

## 命令与迁移

保留 `python -m stgtranscribe.pipeline ...`。新增作品选择 `--game th18`，省略时仍走 TH06；具体 argparse 位置统一写进帮助。新 TH18 `prepare --stage 1` 读取上述清单，再用同一组 `transcribe/review/status/sample` 命令按 `--ids` 处理准备好的单元。TH18 未实现的 `split/extract` 明确提示人工/AI切分＋prepare入口，不能暗落到 TH06。

第一阶段不自动生产整关切分 JSON。AI按现有契约给切分记录，主会话整理/确认清单即可；以后确有批量需求，再单独接 TH18 自动结构摘要和覆盖检查。其他作品必须有自己的适配和已核规则，不能仅凭游戏编号启用。

TH06 暂由适配包住原切分/摘录器，将作品提示词、预算和路径从共用流程移出；保留原命令行为与卡产物。TH18 `out/validate.json` 是新增任务的标准交付，旧TH06任务继续兼容其根目录报告，迁移时更新读写双方而不改旧审核结果。

独立审核仍按源材料推导数值锚点。抽检清单沿用现有方式，Opus抽检与逐条复核由主会话执行；缺 Opus 时明确未完成，不替换模型冒名。TH18首批收卡采用人工确认明确单元后显式调用收卡，拒绝将全部 reviewed 状态静默收进卡池；不新增审批状态机。

## 用户反馈：精简验证（2026-11-05）

新流程不要求给原文、参考页、任务包、目标卡反复计算hash，不新增冻结/签名/防篡改/自动失效机制。来源用文件路径、游戏版本、入口/行号说明，源码修改由Git记录；审阅当前代码，保留必要日志即可。已有历史报告中的hash不抹去，也不作为新通用流程的强制门槛。

机器检查聚焦可执行性：编译、运行诊断、必要的卡元数据、已有段结束与开场规则。语义审核聚焦本任务的原作行为或合成设计要求；不要求每张卡穷尽种子、证明普遍可躲或搭建额外验证项目。现有专项卡的历史验收器不直接推广为所有合成卡的标准。引擎wheel交付已有的依赖一致性要求属于另一范围，不在本轮改动。
